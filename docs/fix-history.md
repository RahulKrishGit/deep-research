## 1. Summary

Deep Research is a multi-agent research CLI built on LangGraph with a DeepSeek (default) or OpenAI chat backend, ChromaDB-backed long-term memory and LangSmith tracing. A question goes through six stages — **planner → researcher → source evaluator → evidence verifier → report writer → report reviewer** — and comes out as a Markdown report, an evidence log, and a machine-readable quality record.

This branch replaced the pipeline's verification core. The old design ran a **fact checker** that spent 61–70% of every run's wall time and 94% of its web searches hunting for a second organisation to confirm figures only one issuer publishes — and across four audited runs it found zero such confirmations, one wrong `contradicted` verdict, and 88 `insufficient_evidence` results. A **critic** duplicated the report review. The branch deleted all three (fact checker, critic, and the synthesizer that became the report writer) and replaced them with an **Evidence Verifier** (a deterministic snippet-on-page check plus one batched LLM Context Check) and a **Statement Check** that verifies every drafted sentence against the findings it cites, judged by a rubric-scored **Report Reviewer**.

The headline numbers, all from independent Fable audits under a single frozen scoring rubric (`scoring-rubric-v1.md`), on the same development question ("Why did the Roman Republic fall?"):

|---|---|---|---|

| 4 | 65/100 | 65.0 | POOR |

Separately, a stall investigation found that live runs were spending large stretches of wall time blocked, not thinking: run 9 took 47m43s, with the researcher stage alone consuming 1,964 s and one call clocking 812.4 s while the event loop sat blocked re-normalising a ~1 MB page once per passage. Fixing that (linear page admission, per-attempt telemetry, and DeepSeek streaming with an idle timeout) cut the verification run to 23m29s, with the same page's researcher stage down to 459 s and the slowest call in that run — 208.5 s — now genuinely generation-bound, not blocked. All 196 provider calls in the verification run completed in one attempt.

## 2. Architecture now

```
Question
   │
   ▼
Planner ─────► targets (required + optional), sub-topics, answer_kind
   │
   ▼
Researcher (ReAct loop, per sub-topic, concurrent) ──► web_search / web_scraper /
   │            document_reader / query_memory                     │
   │            ReadRecord: verbatim body, passages, page_published/updated
   ▼
   Finding: snippet (verbatim), read_id + locator, figures[], content, disputes
   │
   ▼
Source Evaluator ─────► authority score, relay / derivative role, rationale
   │
   ▼
Evidence Verifier
   ├─ snippet-on-page (code, deterministic: excerpt_matches)
   ├─ Context Check (LLM, batched 5/call, ≤8 in flight, no tools)
   │     └─ period / scope / attribution / kind + evidence_words (must be on the page)
   └─ verification: verified | verified_corrected | quoted | dropped
   │
   ▼
Report Writer (parallel: one call per plan "part")
   ├─ per-part draft ──► Statement Check (LLM, batched) ──► consistent / corrected / inconsistent
   └─ bottom line (last call, fed only checked section statements) ──► Statement Check
   │
   ▼
Report Reviewer (one call: scores A1–A7-shaped dimensions, lists missing required targets)
   │
   ├─ material/coverage defect + a pass left ─► targeted extra Researcher pass ─► loop back
   └─ else ─► scoped redraft (named parts only) or publish
   │
   ▼
Publish: report-<id>-0.md · report-<id>-0-evidence.md · report-<id>-0-quality.json
```

Five agents are configurable model roles (`planner`, `researcher`, `source_evaluator`, `evidence_verifier`, `report_writer`); `report_reviewer` is the sixth, a service role. The default stack is DeepSeek chat (`deepseek-flash`, thinking mode enabled, reasoning effort high) with local ChromaDB embeddings (README.md). The evidence contract that makes every downstream check possible: a **Finding** carries a verbatim `snippet` plus `read_id`/`locator` (where it came from) and typed `figures` (`value`, `unit`, `period`, `kind`); its `FindingVerification` records `status` (`verified` / `verified_corrected` / `quoted` / `dropped`), per-figure `matched`/`context`/`evidence_words`, and a reason whenever something is dropped. Only verified figures are cited; every dropped figure is still listed, with its reason, in the evidence log.

The 833 commits split roughly into: 09-16–09-18 (68 commits, early planner/researcher/source-evaluator/claims/fact-checker/critic/synthesizer hardening under the *report-quality-from-live-audit* plan, T1–T4); 09-20–09-23 (256 commits, the evaluation harness maturing from 18 to 31 controlled rows, identity/critic refinements, and controlled real-agent validation); 09-24 (203 commits, the Evidence Verifier cutover — Phase 4 tasks 1.1–4.14, deletion of the fact checker/critic/synthesizer/claim clusters, then the Phase 5 D10/D11 generalization amendment); 09-25 (259 commits, generic-prompt landing, the consumer report format build T1–T6, live runs 3–4 and their fix waves); 09-26 (47 commits, runs 5–10 fix waves, the stall investigation and its fixes, final head `f27ac7e`).

## 3. Fixes ranked by value

Ranked by measured score/defect/time impact where a number exists, then by the severity of the failure removed (honesty breach > fabricated/untraceable claim > halt/crash > material omission), then by generality (helps every question vs. one shape).

### 3.1 The Evidence Verifier redesign — replacing the fact checker, critic and synthesizer

**Problem.** The architecture audit of 2026-09-24 found the fact checker spent 61–70% of every run's wall time and 94% of its web searches trying to find a second, independent organisation to confirm a figure that only one issuer publishes. Across 89 adjudications in four live runs it confirmed **zero** figures with a second source, returned `insufficient_evidence` 88 times, and `contradicted` once — and that one verdict was wrong. It "caused or amplified 16 of about 35 ranked report defects" (figures dropped on re-extraction, claims left unbound to targets, an "Insufficient independent evidence" dump, duplicate bullets, mislabelled contradictions) and "prevented 0-1" real defects (`docs/superpowers/specs/2026-09-24-evidence-verifier-pipeline-design.md` §1). The critic duplicated the report review's job. No stage anywhere checked that a finding's figure actually appeared on its cited page — the honesty rules the project relies on were enforced only incidentally, by scattered researcher/writer checks.

**Root cause.** The pipeline had accreted a corroboration-seeking fact checker on the assumption that a second source should confirm every number; most real-world figures (an agency's own release, a company's own filing) have exactly one authoritative issuer, so that assumption made the fact checker search for something that structurally doesn't exist, over and over, on every run.

**Fix.** Decisions D1–D12 (spec commit `d34fd21` "Spec D8", superseding `ddf1719`/`30a4b79`): delete the fact checker, critic, synthesizer and claim-cluster machinery entirely (no feature flag, clean cutover — D6). Replace them with an **Evidence Verifier** (snippet-on-page in code, then one batched LLM **Context Check** that judges period/scope/attribution/kind per figure) and a **Statement Check** that judges each drafted sentence against its cited findings (D8; implemented `f3c8ac6`, `cdc8ee9`, `8788cec`). The critic is folded into a single **Report Reviewer** call (D5, spec §6.3, `6549eb3`). No corroboration step exists anywhere (D2). The deletion itself landed as `352ea42` ("remove the fact checker, claim clusters, critic and synthesizer and every dead claim-era name") and was merged as `7698fd1` ("Merge Task 4.10: remove the fact checker, claim clusters, critic and synthesizer; exports and pins") — 56 files, +2,203/−62,581 lines.

**Impact.** Structural: three agents and their corroboration search collapsed into two verification stages with no web search at all in verification (D1). All later measured score gains (46 → 84.5) were produced on top of this design; the pre-cutover fact checker/critic path was never scored under rubric v1 because it no longer existed by the time the rubric was written.

**Verification.** `python -m pytest` full suite and `test_state.py` at each merge point (e.g. Task 4.10 integration: 3,703 passed, 2 strict xfail, `test_state` 25); the controlled e2e suite (21/21 at the 4.10 merge, growing to 35/35 by the end of the branch), zero network. `Rev4_10t` and its scoped re-review (`d6146da`) confirmed no coverage regression from the deletion.

**Interview angle.** The lesson is that "independent confirmation" is a policy that only makes sense for a subset of claims (independently measured facts), not a blanket rule; applying it universally turned a verification stage into a search-cost sink with a near-zero hit rate. The fix traded a search-heavy, generic "corroborate everything" step for two cheap, targeted checks — a deterministic string match and one LLM call per batch of five findings — each with a narrow, checkable job.

### 3.2 The final whole-branch review: four merge-blocking defects before the first live run

**Problem.** Before any live run of the new pipeline, a controller-ordered four-slice whole-branch review (`b2fa96b..970b287`, ~22 min/slice) found: **Slice 1 (Critical)** — a relayed figure was credited to the finding's *other* admitted issuer and then folded into a fabricated "earlier edition" (an EIA/Wood Mackenzie example); a null Context Check proposal kept the recorded period or subject, so an *unverified* value could ship labelled `verified`. **Slice 3 (Critical)** — the planner could stamp an organisation the question never named (e.g. "the manufacturer of semaglutide", "European Parliament and Council of the European Union"), making the target structurally unanswerable and forcing a false "Not found" even when the answer existed, at a roughly 30–40% chance on a drawn question. **Slice 4 (P1)** — the "Required targets: X/Y answered" line counted answered *optional* targets in the numerator, so it could print `3/2`; and a spent request budget during the terminal report review escaped uncaught, silently losing a completed report.

**Root cause.** These were integration defects specific to the new evidence contract: the fold logic that merges duplicate/earlier-edition figures did not check that the *same* organisation was the issuer of both; the Context Check's "keep the existing value on a null proposal" fallback had no floor requiring it to have been verified in the first place; and the planner's target-naming had no rule against inventing an organisation the question itself never supplied.

**Fix.** Four fixers dispatched one per slice, each in its own worktree off `4b16143`: `FF1Evidence` (relay-fold correctness, null-proposal honesty, organisation-stamping guard) → `8adcd7a`; `FF2Report` (shared `_carried_rows` rule, Sources, relay label, reviewer prompt sentence) → `f616097`; `FF3Planning` (organisation-stamping guard, guarded first plan review, relative-phrase and `statement_date` fixes, ~246 dead planner lines removed) → `e81f951`; `FF4Orch` (required-target coverage count, publishing under a spent budget) → `02ea00d`. Merged in order as `137c700`.

**Impact.** Full suite went from 3,827 to 3,883 passed (56 new tests) at the merge; controlled e2e 32/32×3, zero network. These were the last defects found before `ev-1` (the first live run) launched — without this pass, an honesty-breach-class defect (a fabricated earlier edition) would have hard-capped the very first audited score at 0 under rubric v1's veto rule (§4).

**Verification.** `ReFix12`/`ReFix34` (combined scoped re-reviews) confirmed every finding addressed with real-graph probes; one new regression the pass introduced (a name-shape rule replacing the role-word blacklist, since the blacklist emptied legitimate names like "Centers for Disease Control and Prevention") was caught and fixed in the same round (`0e38c32`).

**Interview angle.** This is the project's clearest example of "review before the first expensive run pays for itself": four honesty/coverage defects were caught for the cost of a read-only review pass, before a single live DeepSeek call was spent on an audited run. The organisation-stamping bug is also a good design lesson — a planner that "knows" facts from its own training data (the manufacturer of a drug, the co-legislators of a regulation) will happily assert them as if the question had, creating an unanswerable target no researcher pass can ever satisfy.

### 3.3 Verbatim evidence and read provenance

**Problem.** Under rubric v1, "a number or credited statement that is not what its page says is worse than one that is missing" (A2, weight 15) and an untraceable load-bearing figure caps the whole report at 49 (§4). The pre-redesign pipeline had no deterministic, page-anchored contract for a finding's wording.

**Root cause.** `Finding.content` was free prose with nothing tying it back to an exact span of the source text; nothing prevented a figure's period, scope or organisation from drifting away from what the page actually said.

**Fix.** `Finding` gained `snippet: str` (one or two sentences copied verbatim), `read_id`/`locator` (which stored read, and where), and typed `figures: list[FindingFigure]` (spec §4, design doc `2026-09-24-evidence-verifier-pipeline-design.md`). §5.1: the snippet must be contained in the read's stored text under cosmetic normalisation only (whitespace, quote style, hyphenation, case) — `excerpt_matches` — or the whole finding is dropped `snippet_not_on_page`. §5.2: the Context Check's `evidence_words` must independently be on the page, and a period/scope correction is applied only when the corrected wording itself is contained in `evidence_words` or the passage — never guessed. This is the dominant fix line of Tasks T1 (`agents/acquisition.py`, `agents/fact_checker.py`, `agents/source_evaluator.py` passage shaping — 2026-09-23 plan) through the run-3 content wave's S1 slice (`FixSelectionR3`), which later replaced chunk-bounded matching with **whole-page** verbatim relocation: `evidence.locate_snippet` finds a snippet anywhere in the page's joined, normalised text (nearest occurrence to the model's claimed locator), refusing stitched or paraphrased quotes (`ab04359`, `33f707a`). A new `quoted` finding status (`d07cdcc`) lets a figure-less finding that states a fact verbatim, but carries no numeric figure, be cited honestly without being marked `verified`.

**Impact.** By audit-run4 through audit-run9, "untraceable claims: none" appears as a directly-checked line in every audit, verified by the auditor opening every cited page and matching every figure and credited statement by value, period, organisation and kind (honest-pass checklist item 1). No audit in this history recorded an untraceable load-bearing claim.

**Verification.** The snippet-on-page check was replayed on the retained runs against all 25 audit-2 findings and all 34 audit-3 claims, and every one passes it (design doc §1); e2e replay 32/32–35/35 at every point this code changed.

**Interview angle.** "Traceable" only means something if it's independently re-checkable by code, not just asserted by the model that produced the claim — the snippet/evidence_words contract is deliberately redundant: the LLM decides *that* a figure is stated, but code alone decides *whether the words exist on the page*, so a model that invents a plausible-sounding correction cannot make it into the report.

### 3.4 The scoring rubric and the independent-audit loop

**Problem.** Before this, "great" was judged informally; there was no way to say whether run *N* was actually better than run *N-1*, or to compare fixes against each other honestly.

**Root cause.** No agreed, frozen, question-agnostic scoring instrument existed.

**Fix.** The user asked Fable to weight seven dimensions (A1 Parts answered 25, A2 Traceability 15, A3 Honesty 15, A4 Authority 10, A5 Completeness & currency 20, A6 Structure 10, A7 Mechanics 5), define defect classes (cosmetic/minor/material) and a per-item scoring formula (`10 − C − M − X`), and set caps that make the release rule score-only: any honesty breach or invented provenance caps the report at 0; a missing-and-undisclosed required part or an untraceable figure caps at 49; any material defect caps at 69; A1 or A5 below 8 caps at 79; any minor caps at 89. `RELEASE ⇔ overall ≥ 80`. Frozen as `scoring-rubric-v1.md`, with an eight-item "honest-pass" checklist the auditor must satisfy for the score to count (every load-bearing page opened, independent research done, anchors applied literally, borderline calls taken to the stricter class, artefacts audited as published — never re-run or edited).

**Impact.** This is the instrument every other measured figure in this document depends on. It also produced the project's frozen baseline: run 3 (old report format) scored 46.0/100, capped at 49 for an unanswered, undisclosed required part (a "best mic" question with no named product).

**Verification.** The rubric explicitly bars its own drift: "Rubric v1 is used unchanged for every later audit. Any change... is v2 (or later) and requires re-scoring the baseline... so trend lines stay comparable" (§7). Every audit in this history cites rubric v1 and restates the arithmetic (raw score, cap, reason) in its verdict line.

**Interview angle.** A release gate that "acts through the score" (§4) rather than as a separate side veto is a deliberate design choice: it means every fix's value can be stated in points, and a team cannot special-case a bad defect as "not really material" without moving the number.

### 3.5 The consumer report format: answer-first skeleton, question-shaped table

**Problem.** The old renderer (`agents/report.py`, pre-redesign) opened with pipeline counts and plan scope, printed an 8–9-column "Key facts" table with cells reading "not stated" and "(unchecked context)", and closed with an internal "Not found" list. On the run-3 baseline this produced 39 Key-facts rows for about 14 real facts — one headphone's $390 price printed three ways ("390.00 dollars", "390.00 USD", "390.00 $") and filed under the measure "best audio quality" (K001) — while the microphone half of the question was answered by nameless sentences ("this is the model to beat", "the buds'").

**Root cause.** `FactRow.measure` bound to whatever target a finding happened to satisfy, and a finding's binding covered *all* its figures, so a price finding under a sound-quality target printed its price in the sound-quality row. For unscaled dimensions the parser accepted any unit it didn't recognise. There was no structured "which named option does this cell belong to" field at all — a microphone verdict is pure text, so a Microphone column could never exist under the old design (`consumer-report-format.md` §4.4(a)).

**Fix.** SpecReportFormat's answer-first skeleton (title, evidence line, bottom line, question-shaped table, part sections, "what we couldn't confirm", sources) with the table chosen structurally, not by keyword: an **options table** when a required part's checked statements mark ≥2 distinct options (built from `ItemMark`s attached to already-checked sentences — no model call writes table text), else a **findings table** of verified figures when ≥2 qualify, else none (§4.1–4.3). Every table cell is a verbatim span of an already Statement-Checked sentence; publishers and dates are code-derived from `page_credits`. Built as format tasks T1–T6 (`ceb668d` types, `500065e` table, `aa1b7d9` render, `c82fa1e`/`a00c945` writer, `f47da26` reviewer, `92c8936`/`af9b0ec` e2e/merge).

**Impact.** Every audit from run 4 onward reports zero Key-facts-shaped mis-filing defects; the old defect class (a price under a quality measure) does not recur in any of runs 4–11. Run 3, which predates this format, remains the only run scored on the old layout.

**Verification.** A unit fixture built from Fable's own run-3 paragraph (§4.2 "Acceptance fixture") proves the table-choice and cell-construction rules against real headphone data before any live run exercised them; `RevFormatT1T2`/`RevFormatT3` scoped reviews found and fixed a P0 (capped-table caption dropping the forecast/actual label) and P1s (earlier editions printing an unverified vintage; a mark credited to a page the statement never cites) before the format merged.

**Interview angle.** The rejected alternative (§4.4(b): "writer-drafted table rows, each cell a Statement Check item") is instructive — it would have tripled Statement Check volume and let a correction be un-mappable back into a cell. Choosing "code assembles verbatim spans of already-checked sentences" keeps the table's honesty guarantee identical to the prose's, for free.

### 3.6 The parallel report writer with a Statement Check

**Problem.** A single serial writer call for the whole report is slow, and one bad packet can sink the entire report.

**Root cause.** The old synthesizer drafted the whole report in one call, so a single provider stall or one failing part could hold up (or lose) everything downstream.

**Fix.** One call per plan "part," each with only its own bound findings, running in one `asyncio.TaskGroup`; each part's draft is pipelined into its own Statement Check batch under a shared concurrency gate as soon as the draft returns; the bottom line is written **last**, fed only the checked section statements (so it structurally cannot say more than the sections already verified); a redraft after a reviewer defect re-asks only the named parts (spec `consumer-report-format.md` decision 6). Implemented as format task T4 (`c82fa1e`, `report_writer.py` rewritten 1,078 → 1,891 lines) with a scoped re-review addendum (§3.7).

**Impact.** Measured from LangSmith on an earlier serial run: pass 0 = 186 s (draft 102.6 s + Statement Check batches run in parallel at 29.6/24.0/83.8 s). The spec's own estimate for the parallel design is ~125 s per pass `[INFERENCE, stated in the spec itself]` — not independently re-measured in a later live run in these sources. A concrete, later, measured effect is durability: a part whose points were all refused is now disclosed as `failed`, rather than silently vanishing (WholeBranchReview P1-3 fix, `ae6b8ba`), and an all-refused run raises a recoverable `report_writer_all_parts_refused` instead of masquerading as a provider error (`bc7d713`).

**Verification.** Format e2e suite (`FormatT6E2E`) added `ReplayReviewDefect`/`_reply_ScopedReportReviewDraft` doubles and a scoped-redraft-after-a-named-defect case; controlled suite reached 33/33×3 zero network at that point, growing to 35/35 by the branch's end.

**Interview angle.** Making the bottom line the *last* call, fed only checked sentences, is a small ordering decision with an outsized honesty payoff: it is structurally impossible for the bottom line to introduce a claim no section already verified, because it never sees anything else.

### 3.7 The report reviewer and scoped redraft

**Problem.** Merging the critic into the reviewer (§3.1) creates a new problem: after any redraft, does the reviewer have to re-judge the *entire* report again, at full cost?

**Root cause.** A naive merge would re-run the whole review after every redraft, doubling reviewer latency on any report that needed even one fix.

**Fix.** `ScopedReportReviewInput` and `remap_review_for_redraft`: an old→new statement-id map by position across renumbering, a byte-identical check excluding statement ids, and a fallback to a full review when the scoped call fails or the mapping can't be trusted (format task T5, `f47da26`). Iterated hard in review: `RevFormatT5` found a P0 (a scoped re-review silently dropped statement-less new defects, including required-target coverage, so acceptance could flip from a real "major" defect to a false pass) and P1s (remap crossing an iteration boundary; the scoped prompt omitting the full review's judging rules) — all fixed (`acd14c2`, then a second round `9a149cb`/`57c51d9`) before `ReRevFormatT5` closed it clean.

**Impact.** Estimated latency saving (stated as an inference in the ledger, not independently re-measured): "scoped re-review after a redraft... est. −50–60 s on top of the parallel writer's redraft of named parts only" `[INFERENCE]`. The durability win is concrete: `extra_pass_target_ids` now counts material defects only, so a resolved coverage defect no longer buys an unnecessary extra research pass (`9a149cb`).

**Verification.** `ReRevFormatT5` confirmed all findings resolved on a clean archive copy (229 passed); mutation testing on the reviewer's own product code (period match, `_route_defects`, `resolve_attribution`) each flipped exactly the case it was meant to catch (`RevFormatT6`).

**Interview angle.** Scoping a re-review is a correctness trap disguised as a performance optimisation: the first attempt silently regressed acceptance itself, because "only re-check what changed" quietly means "stop checking things that didn't move" — which is exactly where a required-target coverage defect hides.

### 3.8 Output-limit and truncation fixes; the "lift every limit" cutover

**Problem.** Real content was being silently dropped. On run 3 (the audited baseline): `MAX_FINDINGS_PER_SUB_TOPIC=6` dropped 14 findings in one sub-topic alone (the mic topic lost 8); `MAX_UNIQUE_SOURCES_PER_SUB_TOPIC=4` was hit; passage selection deferred 551 passages that were never read; a 4-chunk, 2,400-character per-read admission window meant a semantic answer buried past that window was structurally unreachable no matter how good the ranking was. Separately, planner replies could be truncated by the (then) 32K output cap, triggering retry/redaction logic that itself had a bug: a non-truncation retry failure re-raised the original error content instead of a redacted copy (`RevPlannerRetry`).

**Root cause.** Historical low caps (32K token output limit, small per-read admission windows, small per-sub-topic finding/source caps) were carried forward from an earlier, more conservative design and never re-examined once DeepSeek's real limits (max_tokens 1..393,216; unset defaults 8K/64K/128K by thinking mode/effort) were checked.

**Fix.** The user's explicit ruling: "We should ideally have no strong limits because I want the first version to have good reports... the important right now is quality and latency" → lift every content-dropping cap to generous values or remove it; keep only runaway/loop guards and per-call timeouts. `FixSelection` (`b7a7f8a`): `llm.max_tokens` and the planner-final/report-review/judge/react-decision caps raised to 393,216; a new `agents.re_extraction_max_tokens=32768` scoped to only the owed re-extraction call; `llm.timeout` and per-role overrides raised to 1,800 s. `2d5e24e` (S1, the run-3 content wave): **whole-page admission** — `agents.read_admission_chars=200000` replaces the old per-read passage cap entirely; `agents.evidence_packet_chars=400000` for the extraction packet; a separate `agents.decision_context_chars=24000` bounds only the ReAct decision turns; BM25-style ranking now only orders content, never excludes it; per-sub-topic content caps (findings, sources) raised, then (run-6 wave) turned into pure runaway guards at 120 findings / 48 publishers. `RevPlannerRetry`'s redaction bug was fixed at `fbfc20c`.

**Impact.** Run 3's read-selection `deferred_capacity` of 551 passages and its cap-dropped findings do not recur once whole-page admission lands; a controller real-data check at `845ce34` confirmed all 7 of run 3's own reads were now fully admitted (64/64, 33/33, 208/208, 40/40, 103/103, 56/56, 77/77 passages). Run 6's own trace shows the cap, even after being raised, still discarding 984 of 1,208 proposed findings (81%) in one run — the runaway-guard version (120/48) was set specifically because a hard content cap was still the pipeline's largest single content filter.

**Verification.** RED-then-GREEN tests for every limit change; e2e replay at 32/32 through 35/35 throughout; a dedicated regression test asserts identical admission/verification results between the old and new admission code paths (`RevAdmission` fuzz, §3.3).

**Interview angle.** "Lift every limit" is not free — it directly caused a follow-on performance bug (§3.9, cause A: an O(passages × page-length) re-normalisation that only became visible once pages were admitted whole instead of in small chunks). Removing an artificial content ceiling exposed a real algorithmic-complexity ceiling that had been masked by the small windows all along.

### 3.9 The stall fixes: linear page admission, per-attempt telemetry, DeepSeek streaming with an idle timeout

**Problem.** Live runs took far longer than their generation cost justified. Run 9 took 47m43s; its researcher stage alone was 1,964 s, and its "slowest call" was 812.4 s. The stall investigation (`stall-investigation-fable.md`) reconstructed three distinct causes from LangSmith traces across runs 5–10: **Cause A** (client-side): admitting or cache-revalidating a large page re-normalises the *whole page body* once per passage (`evidence.py` `build_read_record`/`validate_cached_read`, via `excerpt_matches` → `cosmetic_text` on the whole body), blocking the asyncio event loop for 150–342 s at a stretch, with a cache hit validating the same page twice; run 9 alone lost 1,345 s of its 1,964 s researcher stage this way. **Cause B** (provider-side, rare): a non-streaming DeepSeek call sends no bytes during generation, so a dead request is only caught at the full 1,800 s read timeout (run 5 lost 1,800 s + a 222 s retry to exactly this). **Cause C** (the real floor): genuinely long generations at normal throughput (216–245 tok/s) — the planner at `max` effort, 120K-token page packets — which is unavoidable without cutting content.

**Root cause.** `excerpt_matches` normalised the entire page text on every one of hundreds of per-passage calls instead of once; a cache-served read skipped the tool span entirely (so the trace showed no read before the block, only silence); and no per-attempt timing existed to tell a provider stall apart from a blocked event loop or a long-but-healthy generation — the "slowest call" figure conflated all three.

**Fix.** Phase 1 (two parallel slices): **FixAdmission** (`3a99458`) normalises each page's body once per hyphenation mode, lazily, and validates a cache hit once instead of twice. **FixCallTelemetry** (`f243346`, fix round `eacebb6`) adds per-attempt records (start offset, duration, outcome) to every provider span and the Telemetry line, maps `reasoning_tokens`, and starts an event-loop lag monitor (a 1 s ticker recording the worst wake-up delay and any block ≥5 s) for the run's lifetime. Phase 2: **FixStreaming** (`e0e823b`, fix round `f27ac7e`) streams every DeepSeek call with a 150 s idle (inter-chunk) read timeout under the existing 1,800 s total cap — a stalled attempt is now caught at ~150 s instead of 1,800 s — scoped to DeepSeek only, per an explicit user ruling not to touch the OpenAI path.

**Impact.** Offline reproduction on a synthetic 906,307-character page: `build_read_record` 55.8 s → 0.20 s, identical results — **277× faster** (stall-investigation-fable.md §1.2). Live verification (run 11, same question, head `f27ac7e`): total 23m29s (from run 9's 47m43s); researcher stage 459 s (from 1,964 s); slowest call 208.5 s, generation-bound (55,006 output tokens, ~264 tok/s) rather than blocked; all 196 of 196 LLM calls completed in a single attempt, with 0 rate limits and 0 retries.

**Verification.** A counting test asserts whole-body normalisation runs at most twice per admission regardless of passage count; a semantics test proves identical results for hyphen-kept, hyphen-joined and non-verbatim passages; `RevAdmission` fuzzed `3a99458` parent against head on 6,500 cases (65,808 passages) and found byte-identical results with no exceptions — the 1,148 figure sometimes quoted alongside this counts passages that matched only under the lazily computed second (hyphen-joined) normalisation mode, not cases the new code fixed. `RevStreaming` used a real local aiohttp SSE server to time idle timeout (fires at 0.50–0.52 s against a 0.5 s test timeout), keep-alive resets, the total cap, and TCP aborts, with 40 concurrent calls showing isolated per-attempt marks and no leak after 160 induced failures.

**Interview angle.** The **residual** finding from run 11 is itself instructive: loop lag still peaked at 20.8 s with 5 blocks ≥5 s, at stage hand-offs (evaluator/verifier/writer starts), pointing at further per-finding whole-page text work outside the admission path — the fix removed the dominant cause, not every instance of the underlying pattern (client-side CPU work that can still starve the event loop). See §7.

### 3.10 Honesty rules enforced end-to-end

**Problem.** A relay site (a page that republishes another organisation's figure) being credited as if it were the issuer; a forecast printed as if it had already happened; and a report making its own judgement call ("X is the best option") in its own voice, are each an automatic 0 under rubric v1 §4. These recurred repeatedly through the branch's history in different disguises.

**Root cause.** Relay/attribution detection depended on narrow cue lists (`according to`, `reported by`, a possessive) that missed real page shapes — a document's own opening/masthead naming its author, a block quotation introduced only by "To quote X," a self-declared "this is simplified for teaching" disclaimer that the evaluator's four narrow detector patterns did not cover.

**Fix.** Iterative, spanning dozens of commits: relay attribution extended to credit a document's opening/masthead authorship (`d0624d9`, PD-8/PD-18); `page_owner` prefers the page's own stated name when it matches its host (`c70b2a2`); the writer's forecast-verb and actual-verb rules anchored to content, not just tense (run-4 wave, `179ae2d`); a self-declared-kind detector (`derivative_self_description`, run-8 wave `44872df`) reads a document's own "this is teaching material / a simulation / simplified content / an encyclopedia's or chatbot's relay" sentence and scores it as a relay; the report reviewer's own prompt was corrected mid-branch when it would otherwise have flagged 135 of 207 statements in one run as falsely "unsupported" for citing a page or site rather than a named person (`e3f9c3d`).

**Impact.** No audit in runs 4–10 recorded an honesty-breach veto (score-0 cap). The closest call was run 8's material defect: half the bottom line rested on a business-school negotiation role-play whose own footnote said its history was "essentially based on the corresponding entries in Wikipedia and ChatGPT research" and "simplified... for educational purposes" — caught and charged as an A4 *authority* material defect (source standing), not an A3 honesty veto, because the report's words were literally true to the page; the run-8 wave's self-declared-kind detector and authority-ordered registry (§3.13) removed the specific harm the next run.

**Verification.** Each honesty rule shipped with adversarial regression tests (e.g. the run-8 wave's detector, replayed offline against all 70 of run 9's real read records, fired on 0 of them — three real pages described themselves in shapes outside its four narrow patterns, an under-reach rather than a false-positive-free success, see §3.13); Fable's prompt reviews explicitly re-verified honesty wording against the writer, reviewer, verifier and researcher prompts together before every GREEN sign-off.

**Interview angle.** Honesty rules in this project are deliberately layered, not singular: a relay can be caught by the evidence verifier's attribution cues, by the writer's credit rules, by the Statement Check, or by the reviewer — and every layer independently failed at least once in this history, which is exactly why no single layer was trusted alone.

### 3.11 The dissent re-ask and the dispute guards

**Problem.** The single most persistent defect in this entire history: a report stating a mechanism step as settled while its own cited pages, already read by the run, rejected it. Run 4: the Gracchi page's modern-scholarship rejection of the agrarian-decline step, present in the run's own read, never extracted (A5 material, capped the score at 69). Run 5: the same class recurred on Beard's page and the Syme/Gruen paragraph. Run 6: it *worsened* — the disputed Marian-reform step was promoted into the bottom line itself. Run 7: still material, now stated "one line after its own refutation," uncredited.

**Root cause.** The extraction contract's dissent rule was **prompt-only** for three runs straight (runs 5, 6 and 7 — audit-run7-fable.md's attribution table explicitly classes this as "MODEL COMPLIANCE... the extraction rule and its example have not moved the outcome"): asking the model nicely to extract disputing passages did not reliably make it happen, because the model's attention was on its own sub-topic's targets, and a page read for one sub-topic was never re-mined for another's required target.

**Fix.** Turned into **code** only in the run-7 wave (Z1, `1caf5a8`): a deterministic dissent re-ask per admitted read, keyed on a dissent-cue list plus shared key tokens with a kept finding, marking `Finding.disputes=True` and exempting disputing findings from the content cap (up to 4 per target). Iterated hard: `RevZ1` found the two-shared-token rule filtered nothing on real run-7 data (120 of 120 cue passages passed) and reference lists crowded out real slots; fixed by stripping pool-frequent words and ranking by distinct cue then overlap (`5c5578e`). The run-8 wave (`c540fe5`) generalized the underlying researcher subject rule so a passage about a different event/body/product is never bound to a target on a different subject.

**Impact.** Run 8's audit (head `ef95ccb`) confirms both run-7 defects fixed: D1 (A6 material — Marian step stated uncredited and undisputed) "FIXED — every kept point credits a source (`uncited_settled_points: 0`; two uncredited drafts refused before publication)"; D2 (A5 material — the rural-decline rejection) "FIXED — S008 ... the mainstream view among modern historians is that farmers' landlessness was caused by military conscription pressures ... Nathan Rosenstein challenged this in *Rome at War* ... Fifth run; first time written." Run 9 then scored 84.5 with no material defect at all — the first run in this history to clear that bar.

**Verification.** Real-trace probes on run-7 data at every review round: `RevZ1` first found the two-shared-token rule filtered nothing on real run-7 data (120 of 120 cue passages passed); `ReRevZ1` then found 5 of 7 findings resolved on `5c5578e` (reference-list crowd-out, merge mis-bind, flag validation, unmined text — the D2 archaeology passage still qualifies on run-7 data), accepting two as residuals rather than blockers: P1a partial (the packet is hard-capped at 8 passages/8 statements, but qualification stays broad at 120 of 506 passages) and P3c partial (missing unit tests for already-exercised helpers).

**Interview angle.** This is the canonical "prompt-only rule failed three times before it was moved into code" story in this project (see §6) — three separate audits (5, 6, 7) attributed the same defect to MODEL COMPLIANCE against an existing, correctly-worded prompt rule before the team accepted that a purely-instructional fix could not close it.

### 3.12 The uncredited-point guard and its refinements

**Problem.** A report stating a fact with no source at all: run 7's audit found the report's *only* uncredited statement ("Gaius Marius abolished the property requirement... [5][6][30][32][33][34][35][36][37]") sat one line after its own refutation and was carried into the bottom line as settled — a defect distinct from the dissent problem, because here the sentence names no source whatsoever.

**Root cause.** Nothing in the writer's code checked that a drafted point actually named a credit phrase before publishing it.

**Fix.** `_names_a_source` guard added in the run-7 wave (`baa9d20`): a point is refused unless it contains a credit phrase, a reporting verb, an action verb after a name, or a whole name from the finding's site segment, host, attributed issuer or figure organisation. This guard then needed three more review rounds to stop over- and under-firing: `RevZ2` found it vacuous (0 of 46 run-7 statements refused, including the one it was built to catch, because title tokens counted as credit); `1e67fa8` restricted credit to a named phrase or a case-sensitive credit verb; `ReRevZ2` found a title-author-segment loophole letting any capitalised first segment credit; `c0ba781` split "reporting" and "action" verbs into two tiers, requiring a name-shaped subject before an action verb (e.g. "reports," "claims") counts as a credit.

**Impact.** Run 8's audit measured the guard's intended effect directly: run 7's D1 (the Marian step stated uncredited) is "FIXED — every kept point credits a source (`uncited_settled_points: 0`; two uncredited drafts refused before publication)." Run 10's own audit — a later, harder question, run after the guard had shipped — found its over-reach instead: replayed on all eight of that run's refused texts, all eight returned False, because on a rules/constraints question the guard refused legitimate instrument credits ("Article 3(63) defines...", "Article 3(3) defines...") since neither "defines"/"provides"/"requires" counts as a credit verb nor "Article" as a source name — a generalization gap fixed only in the (unmerged) G-wave design (see §7).

**Verification.** Each round included a real-run probe (the "run-7 probe: 45 kept / 1 refused" check, repeated at every subsequent round to confirm no legitimate credit newly broke).

**Interview angle.** A guard defined by *exclusion* (refuse unless X) is safer against fabrication than one defined by inclusion, but every exclusion rule needs its positive counterpart tuned separately per question shape — "credit" means a named person or body on one question and an instrument reference on another, and a single regex-shaped notion of "credit" cannot serve both without generalization work.

### 3.13 Authority ordering and the self-declared-kind detector

**Problem.** Run 8's material defect: half the bottom line, including its terminal causal step, rested on a business-school negotiation role-play that declared itself teaching material — while acoup.blog (15 findings) and the London Review of Books (7 findings), both read by the same run, sat unwritten.

**Root cause.** `is_context_only` (the writer's weak-source demotion gate) had been reverted to unbound-only in an earlier wave (see §6), so a full-standing bound finding from any authority level was cited as-is; nothing ordered the writer's finding registry by authority within a target, and nothing read a document's own self-description of its kind.

**Fix.** Run-8 wave: `derivative_self_description` (`44872df`) reads a document's own declaration and scores it as a relay; a self-declared derivative's registry line carries that description and it counts below the bottom-line authority floor (`d4e8d6a`); the finding registry is now authority-ordered within a target, so the strongest sources get the first labels.

**Impact.** The score jumped from 69 (run 8) to 84.5 (run 9). Run 9's own wave-effectiveness table (§2) records two separate results for run 8's D1: the detector itself **fired on 0 of 70 read records** — three real pages declared themselves outside its four narrow patterns (Classicalia's teaching headings, storiespreschool's "uses material from the Wikipedia article," Grokipedia's "Fact-checked by Grok") — while the **authority-ordered registry** is marked "Achieved: the weak sources (0.20–0.35) were read and left uncited; 24 cited of 56." The appendix's own status line for run 8's D1 says only that "the material harm is gone (no declared derivative reached the report; the invented land ceiling has no counterpart)," crediting neither mechanism by name; of the two, the wave-effectiveness table marks only the registry-ordering entry "Achieved," and the detector's entry "No effect." Run 10's generalization appendix confirms the detector fired 0 of 47 reads there too.

**Verification.** The detector was replayed offline against all 70 of run 9's real read records to get the 0-hit figure, rather than inferred; the registry-ordering effect was checked directly against the cited-source set (24 of 56, all above-floor).

**Interview angle.** This is the project's best documented case of "the fix that shipped is not the fix that worked" — attributing run 9's score gain to the flashier new detector, rather than the plainer registry-ordering change, would have been a wrong lesson to draw forward; the audits' own wave-effectiveness tables exist specifically to prevent that mistake.

### 3.14 The outcome mark and terminal-step rules

**Problem.** A mechanism answer ("why did X fall") that never states what X turned into: run 7's audit found the bottom line ended at "his death creating a power vacuum" with no terminal outcome at all, although a required-target finding stating the outcome, dated, sat citable and unwritten.

**Root cause.** Neither the section nor the bottom-line writer prompt had any rule that a mechanism's *last* step is the outcome the subject actually reached.

**Fix.** Run-8 wave (`d4e8d6a`): the writer marks a point's `outcome: true`; the bottom line lists it under an explicit Outcome block and issues one re-ask when a mechanism answer names no outcome at all.

**Impact.** Run 8's audit: "LARGELY FIXED... the bottom line still ends on a restatement." Run 9's audit: "FIXED. S004 ends the bottom line on the outcome, credited and dated (Actium 31 BCE... Octavian... first emperor)."

**Verification.** Regression run-7-probe replay confirmed the outcome mark fires and the guard's one-shot re-ask does not create an infinite loop; `RevV2` found and fixed a case where the guard fired on a *floor-withheld* outcome (swapping out an already-checked bottom line for nothing), fixed by gating on the filtered label set only.

**Interview angle.** A narrow, mechanical rule ("the last step is the outcome, dated") recovered points reliably once it existed in the prompt with a code-level re-ask backstop — contrast this with the dissent rule (§3.11), which needed to move fully into code before it worked at all; not every prompt rule needs a code guard, but the team's default assumption shifted toward expecting one after three failed prompt-only attempts.

### 3.15 The why/how planner rule and the extraction subject rule

**Problem.** Run 8's audit: the plan added trivia targets no step of the mechanism turned on (a grain law's price, a triumvirate's term of office, troop counts) — filler that displaced real analysis. Separately, a passage about the wrong subject entirely (an "8 Reasons Why Rome Fell" essay-mill page actually about the *Western Empire's* fall, sourced to a historian named Bury writing about 476 AD) was extracted and bound to the Republic-causes target because the extraction contract had no test that a passage's *stated subject* matched the question's subject.

**Fix.** Run-8 wave (`c540fe5`): on a why/how question, an optional target may only ask for a cause, a step, or a dispute — never trivia no step turns on; a passage about a different event, body or product is not a finding for the question's subject, whatever the page's own title claims.

**Impact.** Run 9's appendix: the why/how rule "Largely fixed at the planner: 16 targets, every optional one a cause, a role or a dispute." But the extraction subject rule was recorded as "Not followed" on the very same run: nine Empire-fall findings were still bound to the Republic's topic-01 (the writer simply never wrote them, so no visible harm that run). **The rule did not generalize**: run 10's audit is explicit that this is a *shape-specific* fix, not a general one — "The rule that keeps a mechanism question's required target open... has no counterpart for a rules question, so the planner did to 'obligations' exactly what the P6 rule stops it doing to 'reasons'": it pre-enumerated the answer — Articles 53, 54 and 55 — from its own memory, made Article 54 optional, and left Article 52's notification duty out entirely — the run 10 material defect that capped that audit at 69.

**Verification.** The run-8 wave's own regression tests confirmed the rule holds on the development question; the generalization failure was found by the independent run-10 audit specifically dispatched to test a different question shape, not by a regression test (the planned general-purpose fix, "the constraints counterpart of the why/how rule," was designed in the run-10 fix-wave brief but never landed — see §7).

**Interview angle.** A textbook example of overfitting a general-sounding rule to one shape: "why/how questions get an open required target" reads like a general principle, but its implementation was keyed to the why/how marker specifically, so a "what obligations... and when" question — structurally the same *kind* of problem (an open-ended enumerable answer) — got none of the protection.

### 3.16 Quotation-cue credit and title fallback

**Problem.** Two recurring, smaller honesty/traceability defects: (a) a block-quoted author's words credited to the hosting page instead of the author ("Wikipedia adds that..." for a scholar quoted *inside* a Wikipedia article); (b) page titles that were generic ("Work - ToposText"), truncated by the publisher (Taylor & Francis), or simply the raw `<title>` when a better `h1`/metadata title existed.

**Fix.** Iterative across five runs. Run 4 (`a9284af`): title precedence `og:title` → `twitter:title` → first `h1` → `<title>`, never equal to the bare site name. Run 5–6 (`661106b`, `97c0a29`, `19800e1`): PDF heading fallback restricted to real headings (skipping page numbers, running headers, copyright lines); generic one-word titles ("Work") fall through only when the site's own segment is actually identified. Run 7 (`ea01ff3`, fix round `a3fe008`): a generic title now falls back further — after `h1`, to `DC.title`, `citation_title`, the first `h2`, then the leading clause of `DC.description`, never a heading inside aside, footer or comment chrome — because ToposText serves no `og:title`, `twitter:title` or `h1`, so the run-5/6 rule rejected "Work - ToposText" with nothing better to use; and quotation cues ("To quote X," "in the words of X," "as X puts it") credit the quoted author, restricted to real introducer shapes so a bare "X wrote a book" does not falsely credit X for the page's *own* figure. Run 8 (`31575f3`): a fuller metadata title (`citation_title`, `DC.title`, `og:title`) replaces a publisher-truncated `<title>` it extends.

**Impact.** Run 8's audit: the generic-title fallback was "NOT EXERCISED — no generic-title page among the 44 sources; the fallback code landed (a3fe008)", and the quoted-author defect was "FIXED — quoted authors are credited through their hosts: 'Sallust reports … and Plutarch … as quoted by MIT OpenCourseWare lecture material'". Run 9's status table: the generic-title fallback "fired: 'Work - ToposText' prints as 'Appian, Civil Wars (App.BC)'"; the truncated-title rule was "NOT EXERCISED (no truncated title among 24)"; and one cosmetic of the quotation family recurred (a Wikipedia block quote credited to "Wikipedia", run 9's D8). These remained cosmetic-to-minor items throughout, never material.

**Verification.** Each round added adversarial regression cases (e.g. run-7's fix tested against "Author, Work" first-segment shapes that must credit vs. must not).

**Interview angle.** Individually small, but the volume of iteration (at least seven distinct rounds across five different runs) shows how much of "traceability" work is long-tail string-shape handling rather than one clean rule — real page titles and quotation styles are far messier than a first design anticipates.

### 3.17 The controlled e2e replay harness

**Problem.** Every fix above needed to be checked without spending real DeepSeek calls on every commit, and without depending on live web access at all.

**Fix.** A scripted replay harness (`e2e_evaluation`) that runs a versioned manifest of scenarios against fake providers and fake web/tool doubles, deterministically, at zero network cost. It grew from 18/18 rows (Task 0.1, the branch's very first gate) to 21/21 after the Evidence Verifier cutover, 31/31 and then 32/32 through the Phase 5 generalization wave (new rows for comparison-target-names-both-products and other subject-disambiguation cases), 34/34 through the format build, and 35/35 by the branch's final head — including a dedicated "scoped-redraft-after-a-named-defect" row and an "invalid-scoped-reply-falls-back-to-full-review" row added specifically to exercise paths no earlier scenario reached.

**Impact.** Every merge in this history reports a controlled e2e result alongside the full pytest suite; it is the one gate run at essentially every commit in the ledger, and it is what let the team distinguish "this fix changed behaviour" from "this fix broke something else" without live calls.

**Verification.** `test_e2e_evaluation` itself is tested (case-registry-inventory tests, manifest-version tests); mutation testing was applied to the harness's own assertions more than once (e.g. `RevFormatT6` independently mutated production code and confirmed each e2e row failed exactly its own intended case, not vacuously).

**Interview angle.** The harness's own near-misses are as instructive as its coverage: at one point (`RevFormatT6`) several of its checks were found to be non-discriminating — passing regardless of the code's actual behaviour — a reminder that an e2e suite needs its own review pass, the same as production code.

### 3.18 Earlier hardening on this branch that carried into the final pipeline

The branch's early phases (09-16–09-23, before the Evidence Verifier cutover) did real, tested work under three now-superseded plans: the 09-16 evidence-integrity plan, the 09-23 report-quality plan and the combined expert plan. Most of the code they touched — the fact checker, claim clusters and synthesizer — was deleted wholesale in the cutover (§3.1); what follows is what that work established that still matters, or that no §3 entry above already covers.

**The report-quality-from-live-audit plan (T1–T4, `docs/superpowers/plans/2026-09-23-report-quality-from-live-audit.md`).** T1 (evidence visibility) split a web read's body into bounded paragraph passages so a packet could show the sentence carrying a figure rather than a page's first 1,000 characters (`862370c` "add the versioned read contract and canonical identities"); T3 (research mining) gave every extracted finding the target ids the extraction named and recorded each dated figure's vintage (`20c4e48` "acquire and preserve target-bearing passages"). Both are exactly the shape of the Finding contract the Evidence Verifier still uses today — `read_id`/`locator`, `target_ids`, `release_date`/`vintage` (design doc §4) — so the data model survived even though the fact-checker code it was built for (T1's packet rendering, T2's `claim_clusters.py`, T4's `synthesizer.py`) did not. T4's report-honesty disclosures (run/critic/review status, ranked limitations) were rebuilt once for the Evidence Verifier's own quality gates and then cut again by the consumer report format (§3.5: "Cuts: ... Executive summary, Key facts, Not found, scope"), so none of T4's specific rendering choices ship today.

**The scope test from audit-2 (`c30cda5`, Task 3.1).** Audit-2's worst defect was an all-segment 18.9 GW figure presented as grid-scale; the fix added a scope test to target answering, ruled because "audit-2's worst defect was an all-segment 18.9 GW presented as grid-scale," so a figure's verified scope must match the target's measure, with "grid-scale" and "utility-scale" folded as equivalent. `_SCOPE_EQUIVALENTS = {"grid-scale": "utility-scale"}` is still in `verified_facts.py` today, and the same-subject/scope-matching machinery it introduced is what every later run's fact-row and finding-table logic (§3.5, §3.8) sits on. Audit-2's 25 findings and audit-3's 34 claims are also still cited as the regression fixture the Evidence Verifier's own snippet-on-page check was proven against before any live run (design doc §1; §3.3 above).

**The combined expert plan (S1–S6, `fa46b9d`, 2026-09-23).** The last pre-redesign wave, planned jointly by expert-fable and expert-astra with two user decisions (named-issuer scope; forecasts plus labelled actuals) and landed as one reviewed commit, had six parts: a planner attribution policy (a named issuer's own series earns `primary_attribution`, everything else keeps the independent pair); acceptance of a clean report at the final iteration; research that records the body a page attributes a figure to, and the figure's scope and release date, only where the read states them; a fact-checker issuer badge with provenance carried to the report; a gate lexicon for one measure family; and error-page detection in acquisition. Three parts survive at head `f27ac7e`, checked in code: acquisition still treats a served error page as unusable (`_ERROR_PAGE_MARKERS` in `acquisition.py`); the planner still refuses to infer an as-of cutoff from a bare observation year ("for 2025") while an explicit "as of" phrase freezes it (`planner.py`); and the attribution, scope and release-date fields are part of the Finding contract, admitted only when the read's own text carries them (design doc §4). The attribution policy, the badge and the lexicon are gone: the cutover removed corroboration (D2) and the fact checker with it, and the D10/D11 generality rulings removed domain words from production code, so the lexicon's phrases now appear only in test fixtures.

**The repeated-failed-read halt (`12ed32d`).** A URL that `web_scraper` refused and `document_reader` then also failed recorded two different disposition reasons under one shared key; `merge_evidence_dispositions` treats that as a contradiction, and the graph node turned the resulting `ValueError` into `graph_invalid_agent_state`, ending the run with nothing published over a single bad URL. The fix keys a failed attempt by URL *and* reader *and* attempt number (`_attempt_item_id`), so two tools' failures on the same URL are two facts, not one restated; `_attempt_item_id` is still the disposition key `acquisition.py` uses at head `f27ac7e`.

**The planner output-limit halt and its degraded retry (`14c026e`).** A plan-side structured request (the draft, its lint repair, the review or the confirming review) that reasoned past its output cap raised the non-retryable `ProviderOutputLimitError` and ended the run before any research happened — live run 2's plan call had already used 90% of its budget, and a smoke run hit 77%. The fix routes every plan-side request through one helper, `_complete_plan_request`, that re-asks a truncated request once at `OUTPUT_LIMIT_RETRY_EFFORT` with the same messages, schema and token budget, records the retry's outcome (`planner_output_limit_retry`), and only propagates a redacted failure on a second truncation. `_complete_plan_request` and `OUTPUT_LIMIT_RETRY_EFFORT` are still what every plan-side call goes through at head `f27ac7e`; the same output-limit-retry pattern is what the report writer's and reviewer's own truncation handling (§3.6, §3.8) reuse.

**Credit for qualitative obligations (`4a924e0`, FF1 round 3–4).** A qualitative target (no `unit_dimension`, e.g. "how does the Electoral College work") was answered only when `same_organisation(target.organisation, host-or-attributed-issuer)` held, so a verified text finding from an organisation's own site answered nothing whenever the host didn't spell the organisation's name out (`playvalorant.com` for Riot Games, `ipcc.ch` for the IPCC). The fix made the plan's named organisation the answering preference for a qualitative target — a bound, citable finding answers it unless its page credits a *different* named body — plus fixed `same_organisation`'s leading-article and all-caps-first-word cases. It shipped before `ev-1`'s first live run and is exactly why the Electoral College generality smoke (09-22, head `9589c79`) could answer a rules/process question correctly with no Key-facts figures at all ("the qualitative-target fix at work," per the ledger's own note on that smoke); the same preference-based answering rule is what every later qualitative or text-only target in this history, including the constraints-question runs (§3.15), still resolves through.

**`EvidenceIdentityConflict` (Task 4.10 evidence-core).** Not a halt that was found and fixed in these sources — it is the standing invariant the evidence-merge code raises deliberately when one read, evidence or audit id would silently start carrying two different bodies, a real hazard once whole-page admission and cross-sub-topic mining could touch the same id from two directions (§3.8–§3.9). It is still raised from five call sites in `evidence.py` at head `f27ac7e`; no incident in these sources shows it firing live, so its value here is prevention, not a recorded catch.

## 5. Engineering process

**Audit-driven loop.** Every fix wave in this branch follows the same shape: an independent Fable audit under the frozen rubric produces a defect table with page-level evidence, an attribution table classifying each defect as PROMPT / CODE / MODEL COMPLIANCE / DATA-WEB, and a ranked list of changes by score recovered; a fix wave is dispatched per defect, each fix reviewed, re-reviewed on failure, then re-audited on the next live run. No fix wave in this history skipped the audit step, even under time pressure (see the "speed rules" below).

**Per-slice review and re-review.** Every code change in the ledger went through at least one scoped review (`Rev...`) before merge; a review returning "Needs fixes" produced a fix round, then a re-review (`ReRev...`), sometimes a second (`ReRev...` round 2/3) — the credit guard (§3.12) needed four review rounds before it was accepted as correct on both the credit and the polity-exclusion axes.

**The prompt-review gate.** Beyond code review, every model-read text change (prompts, schema descriptions, tool descriptions, reply examples) went to a separate Fable *prompt* review pass before a live run — a standing gate distinct from code correctness, because a defect can come from wording alone (§3.11's three prompt-only failures are the clearest case).

**D10 and D11: no benchmark words in prompts; general rules only.** After the controller found the phase-5 prompt drafts quoting the benchmark question and naming benchmark organisations directly ("battery storage," "eia.gov/woodmac.com," "about five targets"), the user ruled: "For the prompts, prefer to get great accuracy for variety of questions than overfitting only to certain types of questions" (D10), later extended to every agent and every code path (D11: "domain- and shape-agnostic... any question from any domain... should produce a useful report"). Enforcement was a standing grep gate, run at nearly every merge point in the ledger, checking for probe question terms, domain words, or benchmark organisation names in anything the model reads: the count of model-read strings it scanned grew from `7,331` (`596b9e0`, before run 3) to `8,355` (`07797fa`, before run 7) as the pipeline's prompts grew; the run-8 and run-9 gates (`ef95ccb`, `63b5063`) record only "no new probe-term hits" without restating a fresh total, so the count at the branch's final head (`f27ac7e`) is not in these sources. Every gate from Phase 5 onward reports zero hits.

**TDD, and why wording-pin tests were banned.** Every behaviour change in the ledger shows RED-then-GREEN evidence. A specific anti-pattern was explicitly banned partway through: tests asserting that a literal sentence is present in a prompt ("wording-pin tests"). The reason, stated directly in the ledger: "prompt text is covered by Fable's prompt review" — a wording-pin test locks the current phrasing in place and turns every future prompt improvement into a broken test, without actually testing behaviour. Several were deleted mid-branch by the controller directly, overriding a fix-wave brief that had wrongly permitted them (run-8 wave, V1/V3: "Its 2 instruction wording-pin tests were deleted by Main per the no-pin rule; the brief had wrongly allowed them").

## 6. What didn't work, and lessons

**The target-level authority gate that was reverted.** Introduced in the run-4 fix wave to stop sub-floor sources (a student paper, a legal-dictionary stub) from being cited as full evidence: `is_context_only` demoted a *whole target's* bound findings whenever any citable finding, at any authority, answered the same target. It worked for its intended case, but the run-6 audit found it had also erased **14 of 16** distinct civil-war findings — a single Wikipedia finding touching a target was enough to blank out an entire sub-topic of otherwise-good sources. The run-6 fix wave explicitly reverted it ("Revert my run-4 target-level authority gate, which erased distinct facts; prefer the stronger source in the prompt instead," commit `08fb61d`) and replaced it with a narrower, per-fact "cite the stronger, don't erase the weaker" prompt rule.

**Prompt-only rules that failed three times before being moved into code.** The dissent-extraction rule (§3.11) is the clean example: the same extraction-contract sentence, with an on-point example, was present at runs 5, 6 and 7, and all three audits independently attributed the recurring defect to "MODEL COMPLIANCE" against that unchanged prompt text. Only when the run-7 wave replaced the instruction with a deterministic code-level re-ask (cue detection, shared-token matching, a cap exemption) did the defect clear. The lesson the team drew and applied afterward: a rule whose failure mode is "the model didn't do the thing it was told to do, three times, on the exact case the instruction names" is a candidate for a code guard, not a fourth prompt rewrite.

**Rules written for one question that over-reached on another.** Run 10's generalization appendix names this pattern directly and lists five distinct instances: the dissent-cue list anchored on "however," which is the ordinary connective of a regulatory proviso, not a scholarly rebuttal — so a body's own routine caveat was mis-marked as a dispute and pushed into the bottom line with "but"; the credit guard's notion of "credit" (a named person or organisation) had no concept of an instrument reference ("Article 53(1)(a) requires"), so it refused seven legitimate points on a rules question; the housekeeping/disclaimer rule, built to keep copyright lines out of the report, also swallowed a reproduced provision's own "this text has been amended, not yet updated" notice — which on a rules-with-dates question *is* the answer's currency; and the why/how planner rule (§3.15), whose fix was shape-keyed rather than general. None of these five were "wrong" on the question they were built for; each was silently scoped narrower than its own wording implied.

**The G-wave: designed but not delivered.** A five-slice fix wave (`run10-fix-wave-brief.md`, G1–G5: a general constraints-counterpart planner rule, a dissent-relation field distinguishing `disputes`/`qualifies`/`dates`, an instrument-reference credit rule, a reviewer acceptance-net for uncited required-target findings, and an HTML fallback for `document_reader`) was fully specified and dispatched to fix runs 10's generalization gap. The user then ruled to stop before live verification ("stop the fix wave; no more live runs; run the tests") to move to branch cleanup; the partial planner edit was reverted and both trees were left clean at `f27ac7e`. This is deliberately *not* counted as a completed fix in §3 — it is real, designed, unverified work, listed under Known Open Issues below.

## 7. Known open issues

From `audit-run10-fable.md`'s closing "Not verified" paragraph (Appendix §3) and the run-11 residual, stated honestly rather than smoothed over:

- **The generalization gap itself.** Run 10 (a rules/constraints question) scored 69, capped by a material omission (the Article 52(1) notification duty). The designed fix (§6, the G-wave) was never merged or re-verified live. Any question shaped like "what rules/obligations apply, and when" is at risk of the same class of omission until that wave (or an equivalent) lands and is re-audited.
- **Residual event-loop blocking at stage hand-offs.** Run 11 (post-stall-fix) still showed loop lag peaking at 20.8 s, with 5 blocks ≥5 s, clustered at the evaluator/verifier/writer stage transitions — roughly 45–60 s of the critical path. The stall investigation attributes this to further per-finding whole-page text work outside the admission path it fixed; it was flagged as a follow-up, not fixed, in these sources.
- **The writer's `outcome`/`disputes` point marks are not published.** Two separate audits (run 9 Appendix §2, run 10's closing "Not verified" paragraph) record that whether a given section point actually carried `outcome: true` or `disputes: true` cannot be checked from any published artefact (report, evidence log, or quality JSON) — only inferred from placement. Both audits recommend surfacing these marks for observability; neither records it as done.
- **Whether the evaluator's `source_role` field is populated.** Run 9 and run 10 both note `source_role` stayed `unknown` on all but one or two of dozens of assessed sources per run, even where the rationale text correctly named a page as a relay — the field exists but the model does not reliably set it.
- **The uncredited-point guard's generalization to non-name credits** (instrument references, rule citations) was diagnosed precisely (§3.12, §6) but its fix is part of the unmerged G-wave, not a landed change.
- **Content-type coverage of `document_reader`.** It still fails closed ("unsupported document format") on HTML and PDF-by-content-negotiation responses with no URL suffix — diagnosed as run 10's D6 (it never read the EU AI Act's own EUR-Lex text because EUR-Lex served neither a recognised suffix nor a supported MIME type through that tool), fix designed (G5) but unmerged.

## 8. Glossary

- **Finding** — one extracted fact: a verbatim `snippet`, its `read_id`/`locator`, typed `figures` (value/unit/period/kind), free-text `content`, and optional `disputes`/`dissent_relation` flags. Only `verified`/`verified_corrected`/`quoted` findings can be cited; `dropped` findings are logged with a reason.
- **Read record** (`ReadRecord`) — the stored, verbatim body of one fetched page or document, split into ordered passages, with `page_published`/`page_updated` dates admitted only from real metadata cues (never inferred).
- **Statement** — one drafted sentence (or table cell span) from the report writer, checked by the Statement Check against the specific findings it cites before publication.
- **Target** — one atomic thing the plan requires an answer for; **required** targets must be answered by name or disclosed under "what we couldn't confirm"; **optional** targets exist only to help find a required one and are never a coverage gap on their own.
- **Fable** — `expert-fable`, the read-only senior-advisor agent that wrote the scoring rubric, the stall investigation and every `audit-runN-fable.md`; it never edits code. Names such as `RevZ1`, `ReRevZ1` and `FixAdmission` are the per-task reviewer, scoped re-reviewer and implementer subagents recorded in the ledger.
- **Dissent re-ask** — a deterministic re-extraction pass that re-mines an already-read page for passages that dispute, qualify or date a kept finding, exempt from ordinary content caps, marking `Finding.disputes=True` on a genuine dispute only.
- **Statement Check** — the LLM step (batched, 5 statements/call, ≤8 calls in flight) that judges each drafted sentence against its cited findings' verified figures and returns `consistent` / `corrected` / `inconsistent`; code applies the verdict without re-judging the wording.
- **Context Check** — the LLM step (same batching) that judges, per figure, whether a finding's snippet and surrounding passage state its period/scope/attribution/kind, returning `evidence_words` that code must independently find on the page.
- **Rubric caps** — the score-cap ladder in `scoring-rubric-v1.md`: 0 (honesty breach or no report), 49 (missing-and-undisclosed required part, or an untraceable load-bearing figure), 69 (any material defect, in any item), 79 (A1 or A5 below 8), 89 (any minor defect). `overall = min(raw, lowest applicable cap)`; `RELEASE ⇔ overall ≥ 80`.
- **Band** — GREAT (90–100, cosmetic-only), GOOD (80–89, minors only, releasable), POOR (0–79, any material/veto/answer-item-below-8/minors-pulling-under-80).
- **answer_kind** — the planner's framing classification of the question (`comparison`/`factual`/`historical`/`explanation`/`constraints`); it frames the writer's prompt but never itself chooses the report's table (§3.5).
- **ItemMark / coverage_id** — structured metadata attached to an already Statement-Checked sentence, marking which named option it concerns (`ItemMark`) or which report part it belongs to (`coverage_id`); the question-shaped table is assembled purely from these marks, with no separate model call.
- **Self-declared-kind detector** (`derivative_self_description`) — reads a document's own sentence describing itself (teaching material, a simulation, an encyclopedia's or chatbot's relay) and scores it accordingly; measured to fire on 0 of 70 and 0 of 47 real reads across the two runs it was checked against (§3.13).
- **Authority floor** (`writer_authority_floor`) — the minimum source-authority score a citable finding needs to lead a bottom-line sentence unassisted; historically both under-strict (student papers scoring exactly at the floor) and over-strict (an earlier target-level version erasing whole sub-topics, §6).
- **Honest-pass checklist** — the eight conditions an audit itself must satisfy (rubric v1 §5) for its score to count: every load-bearing page opened and matched, independent research performed, anchors applied literally, every defect tabulated with evidence, untraceable claims stated explicitly (even when empty), borderline calls taken to the stricter class, artefacts audited as published, and the verdict line naming rubric version/raw/cap/overall/band.
- **D-notation** (D1, D2, ... D19+) — numbered decisions recorded in the SDD ledger and design specs as the project's running decision log; a bare "D10" or "D11" in these sources always refers to the generic-prompts and domain-agnostic decisions of Phase 5.
