Status mapping

Five interface statuses, five API statuses, one mapping. Everything below renders from the same tokens the console uses, so the table can be read against the actual chips.

API status running Running · iteration 2 of 3

Text label always present. The dot is redundant reinforcement and is not the only signal.

API status completed + quality accepted Completed · quality gates accepted

Both conditions required. status == "completed" alone is not acceptance.

API status max_iterations · incomplete Partially completed · budget exhausted

Same visual weight as Completed. A normal outcome, not a degraded one.

API status failed Failed · graph_provider_configuration_error

Carries the enumerated error type. Never exception text, never provider text.

Not a status — an absent value Not available while running

No chip, no dot, no icon, no disabled control. Muted text, and nothing else.

Before the first frame Running · stage starting

There is no sixth status. POST /research returns running before any event exists.

Status never depends on colour

The three status hues are close in lightness by design — they sit on the same dark canvas and read as one family. That makes colour a poor sole signal, so every status carries its label. Outline-only chips below simulate the dots losing their hue entirely:

as shippedCompleted
hue removedCompleted
hue removedPartially completed

The words are the signal. The dot is decoration that never has to be read.

State 1 · empty

No session has been started in this process

The history list is empty because nothing exists yet — not because a request failed. The interface says which of those it is.

Reached when

The store holds zero sessions. GET /research/{id}/status for any imagined id answers 404 session_not_found — there is no way to enumerate what does not exist.

The stream is open and has delivered nothing. An empty stream is rendered as an open connection with a zero count and no rows — never as a spinner that implies work is happening, and never as an error.

Report GET /report → 409 session_not_complete

The report is not missing — it does not exist yet, and the server says so with a distinct code rather than a 404. The screen states the code.

State 2 · configuration error

The service cannot start a run, and says why in one word

Preflight runs before a session is registered, so a rejected request produces no session — not a failed one. The distinction matters: there is nothing to retry, only something to fix.

Reached when

preflight() raises ResearchConfigurationError. The route converts it to 500 configuration_error carrying only the enumerated reason — no file contents, no secret values, no traceback.

What the response does not contain

No .env contents, no secret values, no provider text, no traceback. The front end therefore cannot show the operator which key is missing beyond the enumerated reason — and must not guess.

Response body

{
  "error": {
    "code": "configuration_error",
    "message": "Research service configuration is unavailable.",
    "reason": "missing_deepseek_api_key",
    "issues": []
  }
}

The message is a fixed, safe string. The only variable part is the enumerated reason, which is what the panel headline is built from.

Its neighbour: 422

A malformed override is a different failure with a different shape — a list of field locations and types, still without the values:

{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed.",
    "issues": [
      { "location": "body.config_overrides.llm.model_overrides",
        "type": "value_error" }
    ]
  }
}

Both render in the place the request was made — inline on the form, never as a blocking dialog. The design system resolves choices inline; a configuration failure is not a modal.

gapUnreachable without attempting a run

The API exposes no health or preflight route, so this state can only be discovered by submitting. A GET /health returning the enumerated readiness reasons would let the compose screen warn before the operator writes a question.

State 3 · session failed

The run halted, and no artifact was published

A failure is a halt mark in state, not an exception out of the run. Everything collected before the halt survives in the session, but a halted run publishes nothing — so the report endpoint answers 409, not 404.

Reached when

An error type in HALTING_ERROR_TYPES lands in state, or the runner raises. The route to the end is halted and the status is failed.

A finished session with no report is a 409, distinct from the 409 a running session returns (session_not_complete) and distinct from the 404 an unknown id returns. Three different truths, three different codes, and the screen prints the one it got.

The event tail stops where the run did

  1. 17:22:27Zgraph.session.started Session started.
  2. 17:22:31Zgraph.node.started Node planner started.
  3. 17:22:31Zgraph_provider_configuration_error Graph halted.
  4. 17:22:31Zgraph.session.completed status failed, error_count 1, has_report false.

Four frames, then the stream closes. There is no terminal sentinel event: the front end learns the run ended when the connection ends, and must then read GET /status to learn how it ended.

noteNot a crash

The enumerated halt types are outcomes the engine models deliberately. This screen names the type and offers the two things an operator can actually do: fix the configuration, or read the trace. It does not offer to re-run, because the API has no re-run endpoint — the operator submits a new session.

State 4 · partial report

A finished partial run still delivers a report

The refinement budget ran out before the critic accepted. The report exists, is authoritative, and is missing evidence in named places. The interface leads with what the report does say, then states the gaps it declares about itself.

Reached when

status is max_iterations or incomplete, or the route reason was not critique_satisfied — in which case even a completed session renders here with the reason not yet quality-gated.

rulePartial is not failed

A partial run produced its deliverable. The screen uses the same layout, the same type scale and the same action ordering as the accepted report, and the difference is carried by one status chip and the limitations the report already enumerates. Escalating a normal outcome into a warning state would train the operator to ignore the state that matters.
