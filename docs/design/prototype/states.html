Status mapping

Five interface statuses, five API statuses, one mapping. Everything below renders from the same tokens the console uses, so the table can be read against the actual chips.

API status running Running · pass 2 of 2

Text label always present. The pass is read from graph.node.started and graph.extra_pass.started; the ceiling is 1 + max_extra_passes.

API status completed Completed · review accepted · 0.86

completed is exactly the route report_accepted; the score is semantic_review_score, two decimals.

API status max_iterations · incomplete Partially completed · extra passes used · 1 target not found Partially completed · not accepted · 0.71 Partially completed · review unavailable

Same visual weight as Completed. The clause names the outcome: the extra-pass ceiling was spent, a scored review did not accept (or a gate blocked acceptance), or no review score exists.

API status failed Failed · halted

The halting type is the failed stage's headline, in plain words; the chip says only that the run halted.

Not a status — an absent value Not available while running

No chip, no dot, no icon, no disabled control. Muted text, and nothing else.

Before the first frame Running · stage starting

There is no sixth status. POST /research returns running before any event exists.

Status never depends on colour

The three status hues are close in lightness by design — they sit on the same dark canvas and read as one family. That makes colour a poor sole signal, so every status carries its label. Outline-only chips below simulate the dots losing their hue entirely:

One surface is an exception, and it is deliberate. A sidebar row carries no status word: the ledger shows the question and nothing else, and marks a running session with a --status-ok ring. It is not left as colour alone — the ring spins, the row's question steps up to --fg, and the row's accessible name ends in — running. But with animation suppressed the spin is gone, and what separates a running row from a settled one is the ring's hue plus a text-weight step. The words are the signal everywhere else in the product; this is the one place they are not.

State 2 · configuration error

The service cannot start a run, and says why in one word

Preflight runs before a session is registered, so a rejected request produces no session — not a failed one. The distinction matters: there is nothing to retry, only something to fix.

Reached when

preflight() raises ResearchConfigurationError. The route converts it to 500 configuration_error carrying only the enumerated reason — no file contents, no secret values, no traceback.

What the response does not contain

No .env contents, no secret values, no provider text, no traceback. The front end therefore cannot show the operator which key is missing beyond the enumerated reason — and must not guess.

Response body

The message is a fixed, safe string. The only variable part is the enumerated reason, which is what the panel headline is built from.

Its neighbour: 422

A malformed override is a different failure with a different shape — a list of field locations and types, still without the values:

{
  "error": {
    "code": "validation_error",
    "message": "Request validation failed.",

      { "location": "body.config_overrides.llm.model_overrides",
        "type": "value_error" }
    ]
  }
}

Both render in the place the request was made — inline on the form, never as a blocking dialog. The design system resolves choices inline; a configuration failure is not a modal.

gapUnreachable without attempting a run

The API exposes no health or preflight route, so this state can only be discovered by submitting. A GET /health returning the enumerated readiness reasons would let the compose screen warn before the operator writes a question.

State 3 · session failed

The run halted, and nothing was published

A failure is a halt mark in state, not an exception out of the run. A halting node records its error and emits no completion; every later agent node is skipped; the reviewer's route is end, so publication never runs and the report endpoint answers 409, not 404.

Reached when

An error type in HALTING_ERROR_TYPES lands in state. The route to the end is halted and graph.session.completed carries status: "failed".

A finished session with no report is a 409, distinct from the 409 a running session returns (session_not_complete) and distinct from the 404 an unknown id returns. Three different truths, three different codes, and the screen prints the one it got.

Eight frames, then the stream closes. The halting error is not a frame: it is recorded on the session and shown in the failed panel. There is no terminal sentinel event, so the front end learns the run ended when the connection ends and reads GET /status to learn how. Publishing has no frame at all — the graph never runs finalize_report after a halt — so the console marks it skipped from status: "failed", never from has_report.

noteNot a crash

The enumerated halt types are outcomes the engine models deliberately. This screen names the type and offers the two things an operator can actually do: fix the configuration, or read the trace. It does not offer to re-run, because the API has no re-run endpoint — the operator submits a new session.

State 4 · partial report

A finished partial run still delivers a report

Three outcomes land here: the extra-pass ceiling was spent with a required target still missing (max_iterations), a scored review did not accept the report or a quality gate blocked acceptance (incomplete, scored), or no review score exists (incomplete, unavailable). In every case the report exists, is authoritative, and says itself what it could not confirm.

Reached when

status is max_iterations (route extra_passes_exhausted) or incomplete (route report_not_accepted or review_unavailable). completed never lands here: it is exactly the route report_accepted.

rulePartial is not failed

A partial run produced its deliverable. The screen uses the same layout, the same type scale and the same action ordering as the accepted report, and the difference is carried by one status chip and what the report itself says it could not confirm. Escalating a normal outcome into a warning state would train the operator to ignore the state that matters.
